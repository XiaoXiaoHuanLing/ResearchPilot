## 三、Round 1: 单文档问题生成

### 3.1 节点预处理

**过滤逻辑**：剔除不值得出题的"水节点"，同时保留短但高密度的干货内容。

- 旧逻辑：`min_length=80`，一刀切删掉所有短文本 → 丢失含数值/参数/代码的关键节点
- 新逻辑：`min_length=30` + 高密度检测 `_is_high_density_text()`

高密度检测匹配模式：

| 模式 | 示例 | 说明 |
|------|------|------|
| 数值+单位 | `CPU 使用率 > 80%`、`30 分钟` | 含量化的运维指标 |
| 参数赋值 | `log_topic: system-metrics` | 工具参数配置 |
| 英文术语 | `HighCPUUsage`、`SlowResponse` | 告警名/错误码 |
| 代码片段 | `` `query_logs` ``、`` `rm -rf` `` | 工具调用/命令 |
| URL/路径 | `/var/log`、`/app/cache` | 系统路径 |
| 配置块 | `retries: 3` | 配置项 |

**过滤结果**：135 → 108 有效节点（过滤率 20%，保留了大量短但含关键参数的节点）

### 3.2 滑动窗口分组

将同一文档的叶子节点按顺序排列，以 `group_size=5, overlap=1` 切分：

```
节点: [n1, n2, n3, n4, n5, n6, n7, n8, n9, n10, ...]
组1:  [n1, n2, n3, n4, n5]
组2:              [n5, n6, n7, n8, n9]       ← n5 重叠
组3:                          [n9, n10, ...]
```

重叠设计确保跨组边界的信息不会遗漏，相邻组共享上下文。

**分组结果**：108 有效节点 → 28 组

### 3.3 合并 LLM 调用

**核心优化**：将以下 5 项信息合并为一次 LLM 调用输出：

```
旧方式 (5 次调用):          新方式 (1 次调用):
  1. 生成问题                 ┐
  2. 生成答案                 │
  3. 提取原子事实             ├→ 合并 prompt 一次输出
  4. 提取关键词               │
  5. 常识判断 (is_common_sense) ┘
```

合并 prompt 的输出格式要求：
```json
{
  "questions": [
    {
      "question": "问题文本",
      "question_type": "negation/keyword/vague/fact",
      "answer": "完整答案",
      "answer_facts": ["原子事实1", "原子事实2"],
      "key_phrases": ["关键词1", "关键词2"],
      "dependency_node_ids": ["节点ID1", "节点ID2"],
      "difficulty": "easy/medium/hard",
      "topic": "主题标签",
      "is_common_sense": false,
      "why_not_common_sense": "依赖知识库中..."
    }
  ]
}
```

### 3.4 类型多样性约束

Prompt 中强制要求覆盖不同类型，程序层面添加 fact 型上限：

- 每组中 fact 型问题不超过该组问题总数的 30%
- 优先生成多节点综合问题（依赖 2+ 节点的问题优先级更高）

### 3.5 模型 Fallback 机制

主模型 `qwen3.5-plus-2026-02-15` 配额耗尽后自动切换：

```
尝试顺序:
  1. qwen3.5-plus-2026-02-15 (EVAL_LLM_MODEL)
  2. qwen3.5-397b-a17b        (DASHSCOPE_MODEL_NAME_FALLBACK)
  3. qwen3.5-plus-2026-04-20  (DASHSCOPE_MODEL_NAME_FALLBACK_2)
```

触发条件：HTTP 403（AllocationQuota）、429（RateLimit）或连续超时 3 次。

## 四、Round 2: 质量清洗

### 4.1 语义去重 (Embedding + LLM 合并)

**步骤**：
1. 对 83 条问题计算 embedding 向量（`text-embedding-v3`）
2. 两两计算余弦相似度，阈值 0.88 筛出候选重复对
3. 对候选对调用 LLM 判断是否语义等价，等价则合并为一条新问题

**结果**：

```
83 → 83 (合并 0 对，创建 0 条新问题)
```

本次生成的问题差异度较高，无重复对超过 0.88 阈值。此前测试（target=80 时）出现过 77→75 合并 2 对的情况。

### 4.2 批量质量检查 (过广 + 代表性)

一次 LLM 调用同时判断两个维度：

| 检查项 | 判断标准 | 处理方式 |
|--------|---------|---------|
| **过广检测** | 问题过于宽泛，任何相关文档都能沾边 | 有收窄版本 → 替换原问题；无法收窄 → 剔除 |
| **代表性检测** | 问题能否测试 RAG 系统的检索/回答能力 | 无法测试 → 剔除 |

**代表性标准的演进**：

- V1 标准（过于严格）："挖空式、考试型、只需定位文字" → 75 条中仅保留 27 条 (36%)
- V2 标准（当前）：仅剔除"仅凭字面匹配即可回答、答案与知识库无关"的问题 → 83 条中保留 71 条 (86%)

**结果**：

```
83 → 71
  - 过广收窄: 20 条 (替换为更精确的版本)
  - 过广无法收窄: 0 条
  - 不具代表性: 12 条 (剔除)
```

**过广收窄示例**：

| 原问题 | 收窄后 |
|--------|--------|
| "CPU 告警的处理方法" | "CPU 告警触发后，日志查询条件是否只包含 CPU 使用率？" |
| "排查步骤中用到的工具" | "排查过程中查询系统日志和应用日志分别需要使用什么日志主题？" |

对候选对调用 LLM，生成需要综合两个文档信息才能回答的问题：

```
合成 16 条候选多源问题
```

### 5.3 单源验证

对每条候选多源问题，验证其确实无法从单一源文档回答（防止伪多源问题）：

```
验证通过: 16 条 (真多源)
单源可答: 5 条 (剔除)  ← 这些问题表面跨文档，实际从一个文档即可回答
```

**单源验证拒绝示例**：

- "当系统响应缓慢且外部流量持续增长时，应制定分阶段的应对预案..." → 实际上仅 slow_response.md 即可完整回答
- "在系统运维中，面对外部流量和高层内存冲击两种常见告警..." → 仅 memory_high_usage.md 即可回答

### 5.4 合成结果

16 条多源问题均标注 `hop_type: multi_source`，`question_type: multi_source`，依赖节点来自 2+ 个不同文档。

## 七、问题样例

### negation 型 (否定/反转验证)

> **q001**: CPU 告警触发后，日志查询条件是否只包含 CPU 使用率？
>
> 答案: 不是。查询条件为 `level:ERROR OR cpu_usage:>80`，除 CPU 指标外还包含错误级别日志。
>
> 事实: [告警名 HighCPUUsage, 工具 query_logs, 查询条件含 level:ERROR]

> **q006**: 流量突增场景下是否建议采用立即重启服务的处理方案？
>
> 答案: 不建议。流量突增应启动自动扩容/限流，立即重启是死循环的处理方案。

### keyword 型 (关键词检索)

> **q005**: 排查过程中查询系统日志和应用日志分别需要使用什么日志主题？
>
> 答案: 系统日志使用 `system-metrics` 主题，应用日志使用 `application-logs` 主题。
>
> 关键词: [system-metrics, application-logs, 日志主题, query_logs]

### vague 型 (模糊/开放)

> **q003**: CPU 持续超 80% 的危害
>
> 答案: 会导致应用响应变慢、请求超时增加，严重时触发雪崩效应。

### multi_source 型 (跨文档综合)

> **q073**: 在故障处理的短期措施阶段，针对CPU高负载和磁盘空间不足的场景，各自的验证步骤与关键监控阈值标准是什么？
>
> 依赖节点: cpu_high_usage.md + disk_high_usage.md (4 个节点)
>
> 事实: [CPU 验证阈值 <60%, 磁盘验证阈值 <70%, 需持续观察 30 分钟]

> **q086**: 当线上缓存系统出现命中率骤降且数据库压力激增时，如何快速区分是缓存穿透还是配置不当导致的？针对穿透场景的空值请求，以及配置层面的内存占用与过期策略，应分别采取哪些措施？
>
> 依赖节点: slow_response.md + memory_high_usage.md (6 个节点)

## 八、关键设计决策

| 决策 | 选择 | 原因 |
|------|------|------|
| 合并 LLM 调用 | 5 合 1 | 减少 API 开销，避免字段间不一致 |
| 常识判断内置 prompt | 替代独立 batch_check | 省去一轮额外调用 |
| 短节点保留 | min_length 30 + 高密度检测 | 运维文档中大量关键参数在短节点中 |
| 多节点优先 | prompt 强调 + fact 型限流 | 单节点简单问题检索评估意义有限 |
| 代表性标准放宽 | 从"考试型即差"到"无法测试 RAG 即差" | RAG 评估需要事实检索类问题 |
| 单源验证 | 合成后验证 | 防止伪多源问题（实际单文档可答） |
| 断点续建 | 每 5 组保存 checkpoint | 长时间构建中模型配额可能耗尽 |
| 数据备份 | docstore + chroma_db + 源文档 | 防止节点 ID 因知识库变更失效 |
